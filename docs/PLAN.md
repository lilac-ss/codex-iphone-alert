# Codexの完了・承認要求をiPhoneへ繰り返し通知する自作ツール

この文書は、既存の会話で確定した計画を独立プロジェクトへ引き継ぐものです。
この文書は確定要件です。現在の進捗と実機確認の結果は `HANDOFF.md` と `VERIFICATION.md` に記録します。

## 目的

Codexが応答を完了したとき、または承認を求めたときに、Macから離れていてもiPhoneで気づけるようにします。
Macへ戻ってCodexを前面にすると再通知を停止します。

## 確定した方針

- 自分のMacとiPhoneで使う、無料で運用する個人用ツールです。
- Mac用補助ツール、自作Webアプリ、Apple Web Pushを組み合わせます。
- WebアプリはGitHub Pagesで静的配信します。サイトおよび公開用コードが公開される前提です。
- 有料通知アプリ、独自の常設バックエンド、Apple Developer Programへの有料加入は利用しません。
- 初回の端末登録情報はAirDropなどでMacへ渡し、Mac内へ取り込みます。
- 通知内容は固定文と発生時刻に限定します。
- 秘密鍵と端末登録情報はMac内に保持し、GitHubや登録用サーバーへ送信しません。
- MacからAppleのPushサービスへの送信では、配信に必要な購読情報を使用します。
- Codexの既存通知設定を引き継ぎ、導入を取り消せるようにします。

## 実装するもの

### Mac用補助ツール

Node.jsで実装し、ユーザーのLaunchAgentとしてログイン時に起動します。
Web Pushの暗号処理は、バージョンを固定した既存ライブラリを利用します。

Codexのイベント受付と通知の再送管理を行い、Codexの作業を待たせない構成にします。
Mac上で公開HTTPサーバー、外部からの受信ポート、リモート操作機能は設けません。

CLIでは次の操作を提供します。

- 初期設定
- 端末登録情報の取り込み
- テスト通知
- 状態確認
- 通知停止
- アンインストールと既存設定の復元

### Codexのイベント連携

- 完了は `notify` の `agent-turn-complete` を利用します。
- 既存のnotifyコマンドがあれば、引数と振る舞いを保持して呼び出します。
- 承認要求は `PermissionRequest` hookを利用します。
- 通知hookは、承認の許可・拒否やコマンドの書き換えを行いません。
- hookの信頼確認はCodexの標準手順に従います。

現在のデスクトップ版でイベントが期待どおり発火することを実装段階で確認します。
一般的な質問・入力待ちは、初版の通知対象として自動的に追加しません。

### iPhone用Webアプリ

GitHub Pagesに静的PWAを配置します。
iPhoneのホーム画面へ追加したWebアプリで、ユーザー操作を起点に通知の許可を求めます。
購読情報を端末からエクスポートし、AirDropなどでMacへ渡します。

外部のJavaScriptや解析サービスは読み込みません。
初版ではiPhone側からMacへ停止を伝える機能は設けません。
受け取ったPushは、ユーザーに見える通知として表示します。

### 鍵・端末登録情報

VAPID秘密鍵、購読endpoint、認証用keysなどをMac内のリポジトリ外に保存します。
保存先は所有者だけがアクセスできるようにし、ログやエラーにも内容を出しません。
VAPID公開鍵はWebアプリで使用できます。
公開鍵以外の秘密情報や端末登録情報をPagesへ配置しません。

## 通知の動作

1. Codexの完了または承認要求を検知すると、そのイベントを通知します。
2. 未確認の間は1分ごとに再通知します。
3. 各イベントの発生から最大30分で終了します。
4. ロックされていないMacでCodexを前面にすると、保留中の再通知をすべて停止します。

イベントの発生時点ですでにCodexが前面にあり、Macがロックされていない場合は通知を開始しません。
Macがロック中であれば、Codexが前面扱いでも確認済みにはしません。
前面・ロック状態を取得できない場合の扱いは、誤って確認済みとしない方針で実装し、文書化します。

通知本文は、次の固定文と発生時刻だけに限定します。

- Codexの応答が完了しました
- Codexで承認要求が発生しました

会話、ソースコード、コマンド、プロジェクト名、タスク名、実データは通知に含めません。

同じイベントの重複は除去し、複数タスクのイベントは集約して通知数を抑えます。
重複や新しいイベントの発生によって、既存イベントの30分の期限を延長しません。
期限ちょうどの送信を含むかなど、境界条件は実装時に明確にし、テストします。

送信失敗やApple側の一時障害でCodexの処理を停止させません。
Macの再起動やスリープ復帰時には期限切れのイベントを破棄し、過去の通知をまとめて連続送信しません。
停止後でも、すでにApple側へ渡した通知や配送中の通知が届く場合があります。
停止が保証するのは、その後の追加送信を行わないことです。

## 検証

### 自動テスト

- 発生時の送信、1分間隔、30分の上限
- 同じイベントの重複除去と複数イベントの集約
- ロックされていないMacでのCodex前面化による停止
- Macロック中は停止しないこと
- すでにCodexが前面の場合の通知抑止
- スリープ復帰・再起動時の期限処理と過去分の連続送信防止
- 通信失敗・無効な購読情報などでCodexを妨げないこと
- 既存notifyコマンドの引き継ぎと導入解除
- 実イベントpayloadや秘密情報が通知・ログ・公開ファイルに混入しないこと

### 実環境での検証

- 実際のCodexデスクトップで完了・承認要求を検知できること
- 既存の通知と承認の動作を維持できること
- iPhoneのロック画面へ通知と再通知が届くこと
- iPhoneの設定に応じた通知音が出ること
- MacでCodexを前面にすると追加送信が止まること
- 導入解除で追加した設定だけを戻せること

自動テストの成功だけで、実機検証が完了したとは扱いません。

## 前提と限界

- iPhoneはiOS 16.4以降で、Webアプリをホーム画面へ追加する必要があります。
- Macが起動し、スリープしておらず、ネットワークに接続している必要があります。
- iPhoneの集中モード、消音、通知設定に従います。常時鳴るアラームや設定を無視する通知を保証しません。
- 通知の許可と初回の端末登録にはiPhoneでの操作が必要です。
- hookの信頼確認にはCodexでのユーザー操作が必要になる場合があります。

## 作業の順序

1. 専用フォルダ、独立Gitリポジトリ、計画書、開発ルールを準備します。
2. Codexの専用プロジェクトに実装用の新しいタスクを作り、この文書を明示的に引き継ぎます。
3. 新しいタスクで実装と自動テストを完了します。
4. 公開対象を確認したうえでGitHub Pagesへ配信し、Macへ導入します。
5. iPhoneの初回登録と実機での通知・再通知・停止の検証を行います。

プロジェクト準備の段階では、Codex通知設定、hooks、Macの起動項目を変更しません。
既存の会話の履歴が新しいタスクへ自動で共有されることには依存しません。
